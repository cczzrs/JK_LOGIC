# 自定义 JK 节点网络：执行规则与 JSON 契约

本 skill 的设计对象是具有顺序运算、状态和事件语义的自定义 JK 节点网络。AND、XOR 等是解释节点运算的数学函数；`fullAdder` 等名称是生成脚本中的算术辅助方法，不表示产物已经实现为硬件。

## 契约来源与适用范围

本目录 `scripts/engine.mjs` 是独立运行的工作区执行器，SHA-256 为 `c15d5813108c15f8f2736e7c1bbabcdaf23101972e5622b01e81c45289815606`。本版本在原纯数值 Q ID 契约上增加像素后缀的解析、校验和排序支持，未更改 FIFO 运算规则；不再声明它与相邻 `ModelShow/src/engine.js` 内容相同。安装目录中的 skill 和外部 ModelShow 未随此工作区扩展自动更新，含像素后缀的模型须由具备同样 ID 支持的执行器导入执行。这个指纹标识本文件，不证明其他实现或所有模型行为一致。项目根 README 用于说明当前设计定位；此前 README 的历史指纹不作为当前一致性依据。

目标环境更换协议时，应重新比较目标文档、实际引擎、本副本和测试，再一起更新。不将此契约扩展到论文或其他 JK_NET 版本，也不混用 `Qi_q` / `Qi_J0` 等后缀语法。

能力分为三层：

1. **skill 的需求范围**：根据算术、位级布尔逻辑、状态转换及其发送协议，设计节点、`ex`、引用、初始状态和输出映射，并验证功能、状态与事件行为。算术需求可以使用有状态节点或反馈。
2. **现成工具的范围**：CLI 直接生成无符号 `mul/add/and/or/xor`，每个操作数为 1..32 位，采用 LSB-first 和完整输入后排空 FIFO 的协议。Builder 提供基础布尔运算和算术组合方法；`finish` 是这种双操作数协议的 JSON 封装，可追加有状态自反馈输出节点。
3. **需要专门实现的扩展**：有符号、截断、饱和、其他端口布局、通用状态转换、部分或交错输入、其他反馈协议，需要相应的生成逻辑、JSON 封装及独立 oracle。不能只改 `spec` 就把现成 Builder 或验证器变成通用编译器。

## 节点分类和顺序运算

`initial_q` 是节点分类依据：其中出现的 Q 节点有持久的一位 q，初始化设值，执行时从当前 q 开始，完成后写回并发布。未出现的 Q 节点没有持久 q，`ex` 必须以 `J0` 开头，执行结果不保存为下次起始状态。以 `J0` 开头的节点也可以由 `initial_q` 声明为有状态，因此不能根据表达式反推分类。

“无状态”仅指节点不保留上述 q；引擎仍会为它保存外部到达缓存、待执行队列项和最近发布值。网络在不同输入之间是否独立，必须结合这些运行时数据和发送协议判断。

| q | x | Jx = q AND x | Kx = q XOR x |
|---|---|---|---|
| 0 | 0 | 0 | 0 |
| 0 | 1 | 0 | 1 |
| 1 | 0 | 0 | 1 |
| 1 | 1 | 1 | 0 |

`J0` 清零，`J1` 保持，`K0` 保持，`K1` 翻转。各 token 从左到右执行，不能套用传统 JK 触发器的同时输入公式。

语法：`ex := token+`；`token := [JK](0|1|\(source\))`，其中 `source := X(0|[1-9][0-9]*) | Q(0|[1-9][0-9]*)(L[1-9][RGB][0-7])?`，允许忽略空白。Q ID 可为原数值形式 `Q216`，也可为 `Q0L1R0`、`Q215L9B7`：Q 后为全局非负编号，可选后缀表示像素 1..9、通道 R/G/B、位 0..7。X 和 Y 仍只能使用纯数值编号。只能引用 X 或 Q，没有嵌套表达式、算术符号、Y 来源、负编号或前导零。解析器必须消费完整字符串；空表达式和未识别字符报错。`K(X0)` 中括号包的是一个来源，不是子表达式。

以下 a/b/c 须替换成 Xi 或 Qi，**不能直接保留字母变量**：

| 数学功能 | 无状态节点的 ex |
|---|---|
| 0 / 1 | J0 / J0K1（仅初始化发布，见重复输入限制） |
| 复制 a | J0K(a) |
| NOT a | J0K(a)K1 |
| AND a,b | J0K(a)J(b) |
| XOR a,b | J0K(a)K(b) |
| OR a,b | J0K(a)K1J(b)K(a) |
| NAND a,b | J0K(a)J(b)K1 |
| NOR a,b | J0K1K(a)J(b)K1K(a) |
| XOR a,b,c | J0K(a)K(b)K(c) |

局部公式应按所有来源取值组合验证；依赖起始状态的表达式还需包含起始 q。重复来源参与顺序运算多次，但只要求该来源的一次到达。这类局部数值验证不能替代网络事件验证。

## FIFO 激活：缓存、状态和发布

1. **初始化**：设置已声明的 q，不发布 q 初值。所有无来源的有效 Q 节点，无论有无状态，都按 Q 后编号数值排序入队一次；编号相同时按后缀的字符顺序排序，无后缀在前，例如 `Q2 < Q2L1B0 < Q2L1G0 < Q2L1R0 < Q10`。它们的纯常量表达式在执行时才发布结果。
2. **投递与到达**：Xi 和无状态 Qi 是需到齐来源。每个目标按唯一来源 ID 保存独立缓存；部分到达保留，重复到达覆盖最新值。一次来源发布对同一目标只投递一次事件，即使目标的 `ex` 多次引用它；展示多条引用线也不能额外增加执行次数。
3. **入队**：有状态 Qi 不占到齐槽，但其每次发布仍是事件。任一来源事件到达后检查需到齐来源；全部到齐就将缓存值复制为该队列项的不可变副本，并清空该目标的到达缓存。没有需到齐来源的节点，每次来源事件都能入队。相同值再次发布也照常检查和触发，重复入队不合并。
4. **执行**：取出队首。Xi 和无状态 Qi 从该队列项的不可变副本读取，有状态 Qi 则读取执行时的当前 q，可能与先前沿线发布的值不同。顺序计算后先写回本节点 q（若有状态），再发布结果。一次发布激活的目标按上述 Q 编号及后缀顺序追加到 FIFO 尾部；不重新排序整个队列。
5. **输出**：Yi 镜像来源 Qi 的每次发布，不执行 `ex`。未发布的输出为 `null`，不能当成 0。同一 Qi 可以映射到多个 Yi，每个映射都得到发布。
6. **发送**：`send` 先验证所有匹配输入的值，再按 X 编号数值顺序发布已提供输入；不认识的键被忽略，缺失输入不自动补零。一次队列项的计算、状态写回和投递不可被输入打断；调用者只能在队列项之间发送。引擎没有内置轮次、批次或请求隔离。

`queueLimit` 只是 `send` 开始时检查当前队列长度的门槛；它不限制 `enqueue`，一次发送或后续执行仍可使队列超过该值。它不是反馈终止证明，也不是执行总次数上限。需要在明确协议下验证终止；验证脚本的执行步数预算只是有限运行保护，超限不能直接证明数学上的无限执行。

### 随附双操作数工具的发送协议

一次提供完整输入向量，排空 FIFO 后再发送下一向量。这是现成生成器和算术验证器的使用约束，不是引擎新增的批次语义，也不是 skill 对所有需求的限制。每个输出可以在其依赖到齐时先后发布，不承诺所有输入齐后才发布第一个输出，也不承诺各 Yi 原子提交。

对于全部节点无状态、依赖图无环、没有纯常量来源节点且每个 Xi 每次只发布一次的网络，可按依赖关系推导：各节点的唯一来源各发布一次，因而各节点恰好激活一次。随附验证器仍会实际检查每个 Yi 在每轮恰好新发布一次。有状态或有环网络须另外分析，不能直接套用这个无环推导。

不要用纯常量 Q 节点为每轮都需要重新到齐的下游提供参数：它只在初始化发布，后续发送可能一直等待它。可把常量写进 `ex`。需要保留每轮输入事件的常零/常一输出，可使用 `J0J(X0)` / `J0J(X0)K1`。现成封装仍可能产生较长的 `J0K(X0)J0` / `J0K(X0)J0K1`；生成后必须审查并在用户允许优化时按同来源等价规则缩短，不能把旧模板当成推荐最简式，也不能直接删除 X0 引用。

局部 ex 优化应按实际 `initial_q` 分类，保留无状态节点的必要 `J0`、非空合法表达式、唯一来源集合和需到齐来源。只保持需到齐集合还不够：有状态来源不占缓存槽，但其发布仍是事件。依赖初值、恒值来源或可达状态关系的改写必须证明前提在每次相关执行及复位后成立；例如有状态节点初值为 0，不能据此一般性地删除 `J0`。

部分或交错发送可能覆盖缓存，或把来自不同发送的值配成一次执行。skill 可按用户要求设计这类协议，但现成算术工具的通过报告不覆盖它们，须使用专门的状态和事件 oracle。

## JSON 封装和身份

最低可导入例子（复制 X0）：

```json
{"nodes":[{"id":"Q0","ex":"J0K(X0)"}],"initial_q":{"0":[],"1":[]},"q_y":[{"Y0":"Q0"}]}
```

Q/Y 完整 ID 不重复；`Q2` 与 `Q2L1R0` 为两个不同 ID。`initial_q` 的 0、1 列表不重复、不冲突且只引用存在的 Q；`q_y` 每项恰好一个 `{Yi: Qj}`，来源使用相同的 Q ID 语法，例如 `{"Y0":"Q0L1R0"}`。非法引用和异常依赖应在执行前处理。`compileModel` 根据 `nodes / initial_q / q_y` 构建执行结构，根据表达式中实际引用的 Xi 确定引擎输入；额外元数据不能改变节点语义。

现成 `finish` 额外写入 `name`、`format`、`created_at`、位宽、统计、端口、`md5`、`spec` 和 `hash_contract`。它固定使用双操作数布局、无符号、LSB-first 和完整输入排空协议；显式传入的 `architecture/signed/bit_order/a_inputs/b_inputs/output_encoding/input_protocol` 必须与生成封装相同，`spec.input_bits` 若存在必须等于两操作数位宽之和。冲突会报错，不能静默改写。输出位数须为 1..64 且与输出数组长度相同；五种内建操作还要求完整结果位宽。

`spec.nodes/initial_q/q_y/inputs/outputs` 不允许覆盖 Builder 管理的结构或端口。此方法只建立默认无状态节点及可选的有状态输出节点，不提供任意 `initial_q`、状态编码或交错协议的通用封装。扩展需求应专门构造 JSON，并同步定义端口、初值、规格和验证器。

- `format` 是本工具的结构标记 `jk-logic-structure-V3.1.0`，不是读取该字符串就获得的兼容性证明。
- 两个既有英文 `architecture` 值为兼容原模型散列而保留，描述的是无状态依赖结构或追加自反馈输出状态节点，不增加硬件实现含义。现成验证器会核对这两种声明的结构；其他结构需使用明确的自定义描述，仍接受对应数值与事件检查。
- `input_bits` 是声明端口总位数；`inputs` 明列 X0..Xn。现成生成器允许声明但在化简后没有实际引用的输入；引擎只接收实际引用的 Xi。`outputs` 与 `q_y` 应共同覆盖声明的 Yi。
- `jk_bits` 为实际节点数，默认 `jk_bits_max` 也等于实际数。用户给定的容量上限需要单独校验，不能只修改字段。
- `ex_operation_*` 统计清零、常量和重复操作在内的全部 token；`ex_source_max` 为单节点不同非常量来源数量的最大值，`ex_source_sum` 为所有非常量来源 token 的出现总数，重复引用计多次。生成器没有自动记录依赖深度、fan-out 或最大等待来源数；需要这些指标时应补充计算。队列峰值来自具体验证运行。
- `md5` 为 `{nodes,initial_q,q_y,spec}` 的递归对象键排序 JSON 的 UTF-8 MD5，数组顺序保留，小写十六进制。它不包含时间、名称、统计和独立端口元数据，因此不是整份文件的校验和。`hash_contract` 明示算法；`format_md5` 没有本工具定义的算法，默认省略。消费者另有要求时，应取得并实现其契约，不能复制示例散列。
- `created_at` 使用 ISO 8601 UTC；JSON 不含注释、NaN、undefined 或省略内容。识别具体交付版本时同时记录 `md5` 与 `created_at`；同一结构可在不同时间重新生成。
- 模型 JSON 保存结构与 q 初值，不保存运行中的 q、待执行队列、到达缓存等完整状态。重新加载意味着重新初始化，不是继续原执行的 checkpoint。
